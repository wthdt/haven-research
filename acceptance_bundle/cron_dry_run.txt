DELIVERY CONFIRMATION FLOW SUMMARY
========================================================================
1. First run within window:
   - Generates message: "signal_date||避风港 v0.4 收盘更新｜..."
   - Writes close_delivery_pending.json with signal_date, job_id, last_run_at

2. Subsequent runs (same signal_date):
   - Checks close_delivery_confirmed.json → if matches, silent
   - Checks close_delivery_pending.json:
     - If pending matches signal_date:
       - Reads Hermes cron jobs.json for the job
       - If job exists, last_status=ok, last_delivery_error=None,
         AND last_run_at > pending's last_run_at → promote to confirmed
       - Otherwise → retry (output again)
     - If no pending file → first attempt (output + write pending)

3. Next trading day: new signal_date → new ledger entry, cycle repeats.

JOB-STATE BINDING prevents false confirmation when:
  - Hermes crashes before delivery (last_run_at doesn't advance)
  - Duplicate job names exist (_find_cron_job returns None)
  - Stale jobs.json with old last_delivery_error=null
